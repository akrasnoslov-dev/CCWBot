# Event Analysis significance calibration and token efficiency

## Goal

Restore reliable Event Alert significance decisions after the compact-prompt regression without
re-introducing a large per-cycle prompt or deterministic numeric alert thresholds.

Production evidence from the 2026-10-01 13:18:42Z to 2026-10-02 11:37:45Z ops bundle showed
178/178 successful Event Analysis decisions returned `should_alert=false`, including SOL
approximately +4.03% over the analysed 3-hour window. Sanitized reasoning repeatedly described
multi-percent moves as modest/stable. The compact Event Analysis prompt was deployed immediately
before this behavior.

## Clarified requirements

- Keep Event Alert significance LLM-owned. No backend percentage, percentile, volatility, or other
  numeric cutoff may create, reject, suppress, or bypass an Event Alert.
- Add 30-day relative-move context:
  - `p3`: percentile of the absolute analysed-window move versus recent same-symbol historical
    analysed-window moves;
  - `p24`: percentile of the absolute 24-hour move versus recent same-symbol historical 24-hour
    moves.
- Percentiles are evidence only. The prompt must explicitly say they are context, not thresholds.
- If sufficient history is unavailable, send `null`; do not fall back to a deterministic gate.
- Split Event Analysis into two LLM stages:
  1. compact significance decision on every cycle;
  2. alert rendering only when stage 1 returns `should_alert=true`.
- Stage 1 receives only compact decision-relevant market facts and at most two compact candidate
  news items. News remains supporting context and cannot independently create an Event Alert.
- Stage 2 receives the grounded market context needed to produce the existing Event Alert contract,
  including event identity and concise cautious copy.
- Preserve one durable Event Analysis row per symbol/cycle; render is a separate logical LLM
  operation with sanitized terminal telemetry so ops reconciliation remains complete.
- Preserve provider fallback, free-tier constraints, recipient eligibility, four-hour semantic
  cooldown, exact delivery idempotency, and user-facing alert format.
- No database migration.

## Out of scope

- Changing automatic-check cadence.
- Changing Premium/watchlist eligibility.
- Changing the four-hour semantic cooldown.
- Adding paid providers or increasing external service cost.
- Deterministic significance thresholds.
- Production deployment in this task PR.

## Design

### Relative-move context

Use completed historical `event_analysis` rows for the same symbol from the preceding 30 days.
Extract persisted `market.chg_window_percent` and `market.chg24h_percent` from
`raw_input_json`, compare absolute magnitudes, and calculate an empirical percentile for the
current absolute move. Historical rows are observational evidence generated by the existing
deterministic market calculations; they do not encode alert decisions.

The percentile helper must be deterministic, bounded 0..100, and return `None` when history is
insufficient. It must not contain an alert cutoff.

### Stage 1: significance decision

Compact model input should contain approximately:

- symbol;
- analysed-window minutes;
- analysed-window percentage;
- 24-hour percentage;
- 30-day analysed-window percentile when available;
- 30-day 24-hour percentile when available;
- at most two compact selected-news entries: id/title/relevance/material/age.

Output contains only:

- symbol;
- `should_alert`;
- confidence;
- a short constrained reason code.

The prompt defines significance qualitatively and explains percentile semantics, while explicitly
forbidding fixed cutoffs. It must not contain negative-only calibration such as
`routine/modest/stable => false` without equally clear positive calibration around unusual,
fast, or otherwise noteworthy market movement.

### Stage 2: render

Only after stage 1 returns true, call a separate render operation. It produces the existing
schema-grounded positive Event Alert fields: event key, title, body, related-news ids, possible
action, urgency, and confidence. The backend continues factual validation and the market-first
news-only guard.

The render call gets its own logical operation id and a sanitized terminal
`llm_operation_outcomes` row so provider-attempt reconciliation remains correct.

## Acceptance criteria

1. Old compact decision prompt tests fail until the new two-stage contract is implemented.
2. A focused regression demonstrates that a high relative-move percentile is model-visible evidence
   but does not deterministically force `should_alert=true`.
3. Percentile calculation uses absolute historical move magnitudes, is per symbol/window family,
   ignores malformed/unavailable historical values, and returns `None` when history is
   insufficient.
4. Stage 1 prompt excludes full snapshot arrays, previous-alert copy, and verbose news summaries.
5. Stage 1 sends at most two compact news items.
6. Stage 1 output has no title/body/action/event key, reducing completion tokens for no-alert cycles.
7. Stage 2 is never called for `should_alert=false` and is called exactly once for a true decision.
8. Render operation telemetry has a distinct logical operation id and terminal outcome; ops
   reconciliation has no new gaps.
9. No deterministic numeric significance gate exists in production code.
10. Existing factual-grounding, news-only, cooldown, recipient, delivery, and Event Alert rendering
    tests remain green.
11. Deterministic prompt-size tests show the always-on significance prompt is materially smaller
    than the current Event Analysis prompt and document the measured message-character/token proxy.
12. Repository-required verification is green before PR readiness.

## Risks

- Percentile history could be sparse or malformed; treat it as unavailable rather than inventing a
  baseline.
- A second LLM stage could create new rate-limit pressure, but it runs only for true decisions;
  telemetry must make its cost visible.
- Over-compacting news could hide useful context; retain the two strongest already-selected
  candidates rather than adding a new news-ranking policy.
- Changing exact-context semantics can invalidate reuse; version the canonical context when the
  model-visible decision input changes.
- Stage-1 and stage-2 disagreement must not silently flip significance. Stage 2 renders an already
  accepted market event; it does not re-decide `should_alert`.

## Test strategy

Test first:

- pure percentile helper tests;
- compact significance prompt contract and size tests;
- stage-1 schema tests;
- orchestration test proving no render call on false and one render call on true;
- render schema/grounding test;
- telemetry reconciliation contract for the new render call type.

Then run focused Event Analysis tests, LLM config tests, ops-agent tests affected by reconciliation,
and finally the repository checks from `docs/development.md`.
